## What
OQ-059 in `docs/OPEN_QUESTIONS.md`, decided by the user on 2026-11-25 for option (a): publish beside each release the Ubuntu source packages of what the AppImage carries.

## Acceptance
- The Linux release build finds the Debian packages whose files the AppImage carries (from what linuxdeploy copied, or the AppDir's `usr/share/doc/<package>`) and fetches their source in the image at exactly the installed versions (`apt-get source --download-only pkg=version`, with `deb-src` enabled for the pinned release), into one archive per architecture, `Freeloop-<version>-linux-<arch>-sources.tar` (or similar), with a list of package, version and the files of each.
- The release job publishes it beside the AppImage; `SHA256SUMS` and the publish job's exact-file check cover it; the release's notices and `docs/DEVELOPING.md` say where the source is.
- A test (Go or the build's own check) fails when a carried package has no source in the archive.
- `make linux-package` (Colima, arm64) builds it; the archive's size is reported. OQ-059 is closed with the outcome and date.

## Notes
- 2026-11-25: done. `build/linux/sources.sh` (new) finds the Debian package of every file in the AppImage from dpkg's file lists, not only from `usr/share/doc`: a library by the real name of the file the system has under the name linuxdeploy gave it (the unversioned name can be a `-dev` package's link), a `usr/share/doc/<package>` file by its folder. A file no installed package has fails the build unless `ours()` lists it (Freeloop's files, Wails' `AppRun`, the GTK plugin's hook and the three caches it generates). Going by the doc folders alone would have missed 24 packages: the GTK plugin copies every GObject typelib and GSettings schema in the image, from 17 packages with no doc folder in the AppImage (the `gir1.2-*` packages, `gsettings-desktop-schemas`, `libgtk-3-common`, `gcr`, `libglib2.0-dev` for `gschema.dtd`, and `gnome-keyring`, which is installed for the keyring tests and supplies a GPL schema), and linuxdeploy had left out the copyright files of seven libraries dpkg lists under `/lib` (libbz2-1.0, libcap2, libdbus-1-3, libkeyutils1, liblzma5, libpcre3, libselinux1). `sources.sh copyrights`, a new step in `build/linux/Taskfile.yml`'s appimage task before the repack, copies the copyright file of each of those 24 packages into the AppDir. `build/linux/package.sh` then runs `sources.sh archive`, which fetches each source package at the installed source version with `apt-get source --only-source --print-uris <source>=<version>` (which gives the files and their SHA-512 from the index) and curl, checks each file against that checksum, and falls back to Launchpad's `+sourcefiles` when Ubuntu's pool has dropped a superseded version. I confirmed the pool does drop them: gtk+3.0 3.24.33-1ubuntu2.1 gives 404 on ports.ubuntu.com and 200 on Launchpad. I chose `--print-uris` plus curl over `--download-only` for that fallback. It writes `Freeloop-<version>-linux-<arch>-sources.tar` (a folder per source package with the `.dsc` and its files, and `SOURCES.txt` listing package, version, source and the files of the AppImage each gave; tar sorted by name with fixed owner, mode and time, so the same versions give the same bytes), then checks it. `build/linux/Dockerfile` writes deb-src lines for the same mirrors and pockets as its deb lines and fetches the source indexes in the same step as the install. It keeps them (43 MB) and drops the binary indexes, so the versions always match what was installed, however old the image is. `Makefile` `release-linux` copies the archive into `bin/release`, and the `linux-package` help text names it. `.github/workflows/ci.yml`: only package-linux's comment changed, because the release merge step, `SHA256SUMS` and the publish job's exact-file check already cover any file in `bin/release`. `internal/sbom/notices.go`: the Linux notices name both architectures' archives and the release page, with the version filled in, and say that the copyright file of each package is in the AppImage (test: `TestNoticesSayWhatThePackagesCarry`, seen failing first). Docs: `docs/DEVELOPING.md` (linux-package, what a release holds, the notices, and a new paragraph "The source of what the AppImage carries"), `docs/RISKS.md` L-04, `docs/release-notes/0.1.0-beta.2.md`, and OQ-059 closed in `docs/OPEN_QUESTIONS.md`.
- The check (`sources.sh check <AppImage> <archive>`, run at the end of `archive`) works out again from the AppImage what it carries. It fails unless the AppImage holds each package's copyright file and the archive holds each source's `.dsc` and every file that lists, matching its SHA-256, and nothing else. I saw it fail, each time naming the problem, on: no webkit2gtk folder; gtk+3.0 without its orig tarball; a changed pango1.0 debian tarball; an extra file; no `SOURCES.txt`; the AppImage built before this change, which lacks the added copyright files; and an AppDir with a stray `usr/lib/libstray.so.1`. It passes on the real files.
- Run: `make linux-package LINUX_IMAGE=freeloop-linux-arm64-fl085` (Colima, arm64, a clean clone of 80b90bc plus these files, image rebuilt from the new Dockerfile) passed, and so did `make release-linux` after it. Archive: 120 packages from 91 source packages, 417,617,920 bytes (418 MB; webkit2gtk 45 MB, cairo 42 MB, icu 26 MB, gtk+3.0 23 MB, and gcc-12 92 MB for `libatomic1` alone, which is under the GCC Runtime Library Exception and could be left out if the user wants). The second build's archive was byte-identical to the first. The AppImage is 92 MB. `go test -race ./internal/sbom/... ./cmd/freeloop-sbom`, `gofmt -l internal cmd`, `go vet` (also with `GOOS=windows`) and `go test ./internal/archtest/` pass. I checked the workflow offline because it cannot run here: PyYAML and Ruby load it, every `needs` names a job, the artifact names match, and every action is pinned. On stand-in folders, the release job's merge step plus `release-sums` listed both architectures' archives in `SHA256SUMS`, and the publish job's check passed, then failed once an archive was removed.
