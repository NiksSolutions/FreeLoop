## What
From the review of 2026-11-23 (SEC-003, SEC-005), the low-severity permission findings left after issues 061 to 077. Each was confirmed there by a probe against `Broker.evaluate` or by reading; confirm again first.
- **A read, search or think request with no paths is allowed** (`internal/permission/broker.go`, the in-project read policy where `outside` is vacuously false; also the rules-unreadable branch). An ACP agent's `session/request_permission` of kind `search` or `think` with no `locations` is answered "reads inside the project are allowed" whatever its tool touches (`internal/harness/acp/acp.go`, the request mapping).
- **An execute request whose command was not recognised passes command deny rules**: the ACP client takes the command only from `rawInput.command`; with another shape the broker has an empty command, so bypass mode and a tool-wide `allow shell` rule allow it past `deny shell(git push *)`.
- **The macOS sandbox protects the acted-on names only at the project's top level** (`internal/engine/sandbox.go`, against `internal/permission/policy.go`): an unasked sandboxed command can write `src/AGENTS.md`, `sub/.envrc`, `sub/.claude/settings.json`, `sub/.vscode/tasks.json`, which the file tools ask for at any depth. Nested `.git` and `.freeloop` are already covered at any depth; do the same for these.
- **On an HFS+ volume a name with a default-ignorable code point** (U+200C, U+200D, U+FEFF and the like) inside `.git` passes the guard (`internal/permission/policy.go`, `internal/environment/fold.go`); HFS+ ignores them. Strip them in `FoldPath`, as git's `core.protectHFS` does.

## Acceptance
- From an external agent, a read/search/think request with no path asks instead of being allowed by the read policy; the built-in harness, which always names paths, is unchanged.
- An execute request with no command the broker can read counts as unseen while a shell deny rule exists (asks; refused in bypass mode).
- The Seatbelt profile protects those acted-on names at any depth; checked with `sandbox-exec` in a test where the existing sandbox tests do so.
- `FoldPath` drops default-ignorable code points; a test with `.g‌it/config`.
- Tests for each; no new prompts for ordinary requests (the existing suites pass). SECURITY.md updated where it lists these.

## Notes
- 2026-11-24: done. Each finding was confirmed first by a test that failed before the fix.
  - No-path reads: fixed in the ACP mapping, with a flag the broker honours. The ACP client marks every `session/request_permission` as the agent's own (`permission.Request.External`, set in `RequestPermission`, `internal/harness/acp/acp.go`), and `Broker.decide` (`readInside`, `internal/permission/broker.go`) does not count an external read, search or think that names no path as a read inside the project, in the rules-unreadable branch too, so it asks (plan mode included; bypass still allows). Not a broker-wide "no paths, no allowance": the built-in harness does not always name paths. `load_skill` (read), `todo_write` and `task` (think) send none, and that rule would have made them ask. An agent's read that names a file inside is allowed as before. Tests: `TestAnAgentsReadThatNamesNothingAsks` (broker), `TestAnAgentsReadThatNamesNoLocationAsks` (ACP).
  - Execute with no readable command: `hidesFromDenyRules` (`internal/permission/rules.go`) counts an empty or blank command as hiding everything while a shell deny rule exists, so the `unseen` of issue 068 applies: no allow rule approves it, bypass refuses it (with its own reason), and the sandbox asks. The ACP client also reads a command given as a list of words (Codex's `rawInput.command`), quoting each word as for `terminal/create` (`agentCommand`). Without that, every Codex command would have counted as unseen, and been refused in bypass mode whenever any shell deny rule existed. Tests: `TestAnExecuteWithNoCommandIsUnseen` (`hiding_test.go`), `TestAnAgentsCommandInAnotherShape` (ACP).
  - Sandbox: protecting the acted-on names at any depth was built (`anyDepth` in `internal/engine/sandbox.go`, two Seatbelt patterns under its 1024-byte string limit, tested with `sandbox-exec`) and left out by the user's decision the same day, so that criterion is not met. Many npm packages carry `.github/`, `.travis.yml` or `AGENTS.md` (45 entries in a 15,000-file npx install); with them protected, `npm install` in the sandbox leaves them out with `TAR_ENTRY_ERROR`, and `rm -rf node_modules` (so `npm ci`) fails once `node_modules` holds one. The Linux sandbox, which mounts each match it walks read-only, would get a mount for each. Exempting `node_modules` cannot be written safely in Seatbelt (no negation, and a folder can be renamed out of it). The names stay protected at the project's top, and nested `.git` and `.freeloop` at any depth, as before; OQ-060 holds the better design.
  - FoldPath (`internal/environment/fold.go`) drops, before folding, exactly the code points HFS+ ignores and git's `core.protectHFS` (`next_hfs_char`) skips: U+200C to U+200F, U+202A to U+202E, U+206A to U+206F and U+FEFF. It does not drop the whole Unicode Default_Ignorable set. No file system ignores the rest (a zero-width space, the variation selector in an emoji name), so dropping them would only merge names that are different files. Tests: `TestFoldPathDropsWhatHFSIgnores` (with `.g<U+200C>it/config`; the existing APFS pairs unchanged), `TestIgnoredCodePointsDoNotHideProtectedNames` (guard, acted-on, deny rule).
  - Docs: SECURITY.md (the sandbox paragraph, and a section for this issue), ARCHITECTURE.md (the evaluation order).
  - Not changed (outside this issue's files): `Engine.CheckPolicy` (`internal/engine/policy.go`) never sets `External`, so for an external agent's session it still says a search with no path is allowed while the broker would ask.
