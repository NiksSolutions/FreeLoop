## What
OQ-052 in `docs/OPEN_QUESTIONS.md`, decided by the user on 2026-11-25 for the recommendation: a stolen, unlocked phone holds a 90-day key; an approval from the phone asks for a passkey (Face ID or Touch ID) again after 18 hours. The tailnet name is now a stable origin (GUI-052, `remote.host`).

## Acceptance
- At pairing, the phone app creates a passkey for the tailnet host (WebAuthn, platform authenticator, user verification required) and the server stores its public key with the device; a phone paired before this asks to add one, and until it has one it cannot answer approvals.
- An answer to a permission request from the phone (and anything else that lets a session act: sending a prompt is decided in the notes) needs a passkey check less than 18 hours old; otherwise the phone asks for one first, then sends the answer. The server verifies the assertion: origin and RP ID, challenge it issued (single use, short-lived), user verification flag, signature with the stored key, sign count not going backwards.
- No new dependency: the key comes from `getPublicKey()` at registration (SPKI), verified with Go's standard library; if that proves impossible, stop and report rather than add one.
- Removing the phone removes its passkey record. Tests in `internal/remote` with a software authenticator; phone unit tests; app check steps where WebAuthn can be stood in for; words in en, de and nl. REQUIREMENTS (GUI-052, SEC-020), SECURITY and the phone help say so. OQ-052 is closed with the outcome and date. The real iPhone check is added to issue 025.

## Notes
- 2026-11-25: built. Server: `internal/remote/passkey.go` (new) with `GET /api/passkey`, `POST /api/passkey/challenge`, `/register` and `/verify`; `POST /api/decide` and `POST /api/sessions/{id}/prompt` now go through `checked`, which answers 403 with `passkey: missing | stale | pair-again` unless the phone's last good check is under 18 hours old (measured on the server; a clock put back counts as stale). Relying party `remote.host` (lower case, no port), origin exactly `https://<host>:8443` (`engine.PhoneHTTPSPort`, the port the shown `tailscale serve` command uses). Registration: platform authenticator, `userVerification: "required"`, `attestation: "none"`, ES256 only; the key is the SPKI from `getPublicKey()`, read with `crypto/x509` and required to be P-256; the client data (`webauthn.create`, challenge, origin, not cross-origin), the RP ID hash, UP and UV, and the credential ID in the authenticator data are checked; no CBOR is read. Assertion: a 32-byte challenge per phone (the newest, single use whatever the outcome, two minutes), client data `webauthn.get`, RP ID hash, UP and UV, ECDSA signature over authenticatorData || SHA-256(clientDataJSON) with `crypto/ecdsa`, and a counter that may not go back or stand still unless both are zero. No new dependency. Stored in `devices.json` on the device (`config.Passkey` in `internal/config/remote.go`: ID, SPKI, algorithm, RP ID, counter, added, checked), so removing the phone removes it; pending challenges go too.
- Decided here, as the issue asked: **sending a message needs the check too**, not only answering a request. A message can make an agent act within its mode (in bypass or with allow rules, without asking anyone), which is what a stolen phone must not do; and one Face ID covers both for 18 hours, so it adds no prompt in practice. Reading, streams, pictures, Stop, push settings and signing out need only the key. **Making the passkey counts as a check** (the user was verified for it), so pairing asks for Face ID once, not twice; the check after that comes 18 hours later.
- A phone with a passkey cannot make another with its key alone (409): whoever holds the key could otherwise swap in their own. A new one comes with pairing again, also when `remote.host` changed (`pair-again`). Left as it is, and said in SECURITY.md: a phone paired before this change, or one that chose "Not now" at pairing, makes its first passkey with its key alone, so until it does, whoever holds that key could add theirs; Settings → Phone now lists "no passkey yet" for such phones, and pairing again closes it.
