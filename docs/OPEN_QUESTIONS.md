# Open questions

Decisions not yet made, each with options, a recommendation and the milestone by which it must be settled (see [ROADMAP.md](ROADMAP.md)). Closed questions move to the bottom with their outcome.

## Open

- **OQ-044 · A native sandbox on Windows · needed before "Local, sandboxed" is offered on Windows.** Seatbelt (macOS) and bubblewrap (Linux) have no cheap counterpart on Windows. Options: an AppContainer with a capability-less token, the project and caches granted by ACL and everything else denied by the container's own isolation (closest to the other two, but every grant is an ACL change on the user's files, and console programs and Git Bash need testing inside it); a restricted token with a low integrity level (simpler, but it only blocks writes to medium-integrity places, so reads of secrets are not stopped); Windows Sandbox or Hyper-V (strong, but a whole VM, Pro editions only); WSL with bubblewrap inside (reuses OQ-037, but a project on the Windows drive is slow there and WSL must be installed). *Decided for now, 2026-11-08, by the user:* none. On Windows, "Local, sandboxed" says plainly that Windows has no native sandbox yet and points to the Docker environment, which confines an agent's commands as well and works through Docker Desktop. Recommendation for later: AppContainer, built and tested on a real Windows machine with the containment tests of `TestSeatbelt*` turned into Windows ones.

- **OQ-051 · The phone without Tailscale · needed when users without Tailscale ask.** Options: (a) a self-hostable relay that forwards only end-to-end encrypted messages (Noise, keys paired by QR), as Happy does, with the phone app served from a fixed address; (b) the same LAN only; (c) Tailscale only. Recommendation: (a), as its own plan, since it needs the phone app hosted somewhere and a key exchange of its own.
- **OQ-061 · What else Git for Windows keeps in its system config · needed before a Windows release.** Under OQ-046's (b) the app's git gets only `core.autocrlf` and Git Credential Manager from the system config. Git for Windows' installer also puts there the Git LFS filter (`filter.lfs.*`), the TLS backend and certificate file (`http.sslBackend`, `http.sslCAInfo`) and Azure DevOps' `useHttpPath`, and users add `core.longpaths`. Without the LFS filter, in a repository that uses LFS on a machine where `git lfs install` never wrote it into the user's global config, a file can show as changed and a commit from the diff panel stores the file itself instead of its pointer (`git add` without the filter does, tried on a Mac). Without the certificate file an https push may not verify the server; not tried. *Since 2026-11-25 the TLS settings are passed:* `http.sslbackend` (openssl or schannel) and `http.sslcainfo`, to the commands that reach a remote, each only where the user's own config does not set it (`systemGitPairs`, `TestSystemGitKeepsTLS`, `TestSystemGitTLSReachesNetworkCommands`); the LFS filter, `useHttpPath` and `core.longpaths` are still open. Options: (a) pass these too when they are Git for Windows' own: the filter only as `git-lfs` with its usual arguments, the TLS and path settings, which name no program, as they are; (b) pass the TLS settings, and refuse the panel's stage and commit where `.gitattributes` names a filter git has no config for; (c) leave it. Recommendation: (a), once the first run on Windows (issue 055) shows which of them are missed.

## Closed
- **OQ-024 · A Client ID Metadata Document for MCP sign-ins · closed 2026-11-27 (the user took the recommendation, GitHub Pages).** `site/oauth/client-metadata.json` is the document, served by GitHub Pages from the repository (`.github/workflows/pages.yml`) at `https://nikssolutions.github.io/FreeLoop/oauth/client-metadata.json`, which is its `client_id` and the address the app sends (`clientMetadataURL` in `internal/engine/mcpoauth.go`). It names the app, lists the `authorization_code` and `refresh_token` grants, no client secret, and the redirects the app can send: three fixed loopback ports, 23817 to 23819, which a sign-in's callback tries first, one per server (a server that compares redirect URIs exactly, as the spec has it validate them against the document, accepts only these), and the port-less loopback for servers that take any port, as RFC 8252 asks, which the free port a server falls back to needs. The order follows the MCP authorization spec: a client ID the user entered, then the document where the server advertises `client_id_metadata_document_supported`, then Dynamic Client Registration. The address is tied to the repository's owner and name: a move breaks it for authorization servers that cached it, so a move needs the old Pages site kept or the document published where a project domain can carry it; a project domain, if one comes, replaces it.

GStreamer's PulseAudio source has been in `gstreamer1.0-plugins-good` since 1.18 (`gstreamer1.0-pulseaudio` is an empty transitional package), and `libwebkit2gtk-4.1-0` depends on it; the `.deb` recommends it and only suggests `gstreamer1.0-pipewire`. Tried in the Linux build image under Xvfb with WebKit's mock microphone, in the app and in a probe: the app's page gets a track and the capture worklet runs; a page elsewhere in the window, the camera and frames of another origin get nothing. A real microphone on a Linux desktop is for issue 055. - **OQ-046 · Git's system config on Windows · closed 2026-11-25 (the user took the recommendation).** (b) where the system's credential helper is Git Credential Manager by its own path, otherwise (a). The app asks git once a run what its system config sets of `core.autocrlf` and the credential helpers (`git config --system --includes -z --get-regexp`; `systemGitOf` in `internal/engine/git.go`). Git Credential Manager by its own path is `manager`, which Git for Windows writes and git runs as `git-credential-manager` from its own folders; `manager-core`, its older name; or an absolute `C:/...` path to `git-credential-manager.exe` (or `-core.exe`) with nothing after it and nothing the shell reads but an escaped space or bracket. Every helper left after the last empty `helper =` must be one of these, and none may be for one address. Then the app's git calls and its push keep `GIT_CONFIG_NOSYSTEM=1` and get each helper with `-c credential.helper=...`, exactly as configured, and `-c core.autocrlf=...` for a command that converts line endings where neither the command, the repository nor the user's global config sets it, which git is asked first: on the command line it would win over those, while git reads the system's value below them. gh's git calls get the same through `GIT_CONFIG_COUNT`. Any other helper (`wincred`, `store`, another program, one with arguments, a shell snippet starting with `!`), a helper for one address, no helper or no system config, and git reads the system config with hooks pointed at a folder under `%SystemRoot%\System32` that does not exist, as built on 2026-11-08 (a). A repository's own config still cannot add a helper: the push refuses `credential.*helper` there. Unlike git itself under (b), the system's helpers come after the user's global ones rather than before, and a global empty `helper =` does not drop them; the rest of the system file stays out (OQ-061). Tested on a Mac with stand-in system files read by a real git (`TestSystemGitConfig*`); what to check on Windows is in issue 055.

- **OQ-034 · How an SSH environment holds the project** · closed 2026-11-04 (the user asked for this model, and for it to be as secure as possible). A working copy per session on the other machine, kept in sync, with the project staying on this Mac: the app's git, diffs, checkpoints and worktrees keep working, about 80 uses of a local path need no change, and the other machine is a boundary an agent's commands stay behind. The other option, a project that lives only over there, suits repositories too big for a Mac and would need all of those reworked; it would be a new kind if asked for. The sync does not use rsync, which was the first plan: pulling from a machine that may be compromised would run rsync's receiver here against a hostile sender (CVE-2022-29154, CVE-2024-12086), so what comes back is a name list and a tar stream that Go reads as data. The other machine needs a POSIX shell, `tar` that takes `--null -T -` (GNU or BSD), `find`, `xargs`, and `git` if the copy should have a repository; BusyBox's `tar` is not enough. What it costs: only regular files come back with no executable bit, some files must be copied by hand, and a command's sync adds round trips.

- **OQ-037 · The Linux sandbox · closed 2026-11-08 (the user chose bubblewrap, and for localhost the sandbox's own loopback with `pasta` when installed).** "Local, sandboxed" on Linux runs each command under bubblewrap (`bwrap`), as Seatbelt does on macOS. Seatbelt allows by default and denies; bubblewrap builds the command's view of the system from mounts, so each guarantee maps as follows. *Processes:* a private process namespace (`--unshare-pid`, `--new-session`), so no other program can be seen, signalled or read, and no terminal can be fed input. *Files:* the root read-only; the project, its caches and temp files writable (read-only in plan mode); the home folder replaced by an empty one with only the project, caches and listed toolchains mounted back; protected paths under the project mounted read-only; folders that must not be moved (`.git`) mounted on themselves, which makes renaming them fail; what is never readable (the data folder, a deny rule's paths) hidden under an empty folder or file, with the skill store mounted back. *Sockets:* `/tmp`, `/run`, `/var/run` and the home folder are fresh, so the Docker socket, the SSH agent, the D-Bus session bus and the keyring are out of reach; with no network, abstract sockets are too. *Network:* none is a private network namespace; all shares the host's; localhost is a private namespace whose loopback holds only what the sandbox starts, unless `pasta` (package `passt`) is installed, which then forwards the host's listening loopback ports into it, as on macOS; listed hosts reach the app's egress proxy through a socket mounted in and a bridge inside the sandbox. *Built 2026-11-08* (`internal/platform/linux/network.go`, `internal/environment/bridge_linux.go`), pinned to pasta 2024-02-20, Ubuntu 24.04's; Ubuntu 22.04 has no `passt` package. With pasta, a command runs as `pasta -q -f -t none -u none -T auto -U none -- bwrap ...`: pasta makes the network namespace and forwards the host's listening loopback TCP ports into it, checking each second, so a dev server started later is reached too; nothing is offered the other way; its interface stays down with no address or route (no `--config-net`), so nothing beyond loopback is reached. bwrap starts as root of pasta's user namespace, which owns that network, and could then bring the interface up, so it gets `--unshare-user --uid <user> --gid <group> --cap-drop ALL` (tried: without them, a command configured the interface). UDP is not forwarded, since a host's name server on loopback would let a command send data out by name lookups, which macOS's sandbox does not allow. That pasta does not start without a default route and warns on the command's output about a family with none, so the sandbox checks `/proc/net/route` and `/proc/net/ipv6_route` first, passes `-4` or `-6` when only one has a default route, and with neither, offline, keeps its own loopback (pasta from 2026 starts offline; the check is kept for 24.04's). The listed hosts with pasta reach the proxy as a forwarded port, as on macOS; without pasta, the app's proxy also listens on a Unix socket in `~/.cache/freeloop/egress/`, bound into the sandbox at `/run/freeloop/egress.sock`, and the app's own binary, bound at `/run/freeloop/bridge` and run with the hidden argument `sandbox-bridge`, binds `127.0.0.1:<the proxy's port>` inside, leaves a server for it behind (through a second process that exits, so the command is not its parent), and becomes the command, so the command keeps its exit status and signals. The bridge needs nothing installed. None has neither pasta nor the bridge. *Not carried over:* a protected path that does not exist when a command starts (a new `AGENTS.md` or git hook) cannot be mounted read-only, and a deny rule's wildcard covers only what matches when a command starts; the file tools still refuse both, and hooks and settings files still wait for approval, but a sandboxed shell command could create them. bubblewrap needs unprivileged user namespaces; where a distribution turns them off, or AppArmor withholds them (Ubuntu 24.04 grants `bwrap` its own profile), the environment's self-test fails and its commands do not run, as with a sandbox that cannot start on macOS.
